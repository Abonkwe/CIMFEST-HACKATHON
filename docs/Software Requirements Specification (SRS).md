# Software Requirements Specification (SRS)

**Project:** BeatToons (working name) – a Cameroon-first music challenge platform **Event:** CIMFEST Hackathon 2026, Track 2: Music & Entertainment Tech **Version:** 0.1 (hackathon draft) · **Date:** 23 November 2026 **Team:** *\[add team names\]*

## 1. Introduction

### 1.1 Purpose

This document specifies what the platform must do. It guides the team during the 48-hour build, keeps scope under control, and gives the AI coding assistant a precise brief.

### 1.2 Product vision

A social platform built in Cameroon for Cameroonian music, creators and culture. Fans turn trending Cameroonian songs into funny character animations, compete in time-limited challenges, and vote for the best. Artists get discovered, and creators without money or a camera get a stage.

### 1.3 Scope

**In scope for the hackathon MVP:** Cameroon Trending feed, song clips, Animation Studio Lite, time-limited challenges, posting to a feed, voting, leaderboards, phone-based sign-in, basic artist verification flow.

**Out of scope for the MVP (mock-ups or roadmap only):** full music distribution to streaming services, payouts and tipping, sponsored-challenge management, comments, follows, direct messages, a full recommendation algorithm.

### 1.4 Definitions

| Term | Meaning |
| --- | --- |
| Artist | A verified Cameroonian musician who uploads songs |
| Creator | Any user who makes an animation for a challenge (can be anywhere in the world) |
| Fan | A user who watches and votes |
| Clip | A short excerpt (15–30 seconds) of a song used in a challenge |
| Challenge | A time-limited contest around one song clip |
| Creation | A creator's character animation submitted to a challenge |
| Fresh pool | The set of new songs shown to a small sample before reaching Trending |
| Admin | A team member who reviews artists and moderates content |

## 2. Overall description

### 2.1 Problem statement

Emerging Cameroonian artists struggle to be heard. Fans want to take part, but most creative tools require a camera and editing skills. Existing platforms are global, so local music is easily buried, and reach often goes to those who can pay.

### 2.2 Users

| User class | Goals |
| --- | --- |
| Fan | Discover Cameroonian music, watch creations, vote |
| Creator | Make an animation quickly, enter challenges, win recognition |
| Artist | Upload songs, see engagement, get discovered |
| Admin | Verify artists, remove harmful or copied content |

### 2.3 Operating environment

A mobile-first web application that runs in modern phone browsers, works on slower connections, and is also usable on desktop. *\[Tech stack to be confirmed by the team.\]*

### 2.4 Design principles

1. **Cameroon first:** local songs, languages (English, French, Pidgin), humor and regions.
2. **Fair reach:** reach cannot be bought; it is earned through votes and engagement.
3. **Simple:** a new user can create a post in under a minute.
4. **Light:** short clips and small pages to save data.

### 2.5 Assumptions and dependencies

- The demo uses royalty-free tracks or clips from artists who have agreed.
- A phone verification service (OTP) is available, or a mock OTP is used for the demo.
- Characters and sprites are drawn or generated by the team before the build starts.
- An AI coding assistant (Google Antigravity or similar) is used to accelerate development.

### 2.6 Constraints

- 48 hours total, a team of 3–5.
- Mobile-first, low-bandwidth friendly.
- Music rights: only licensed or opted-in content may be streamed.

## 7. Key use cases

**UC-1: Create and enter a challenge**

1. The creator opens Trending and picks a song with an active challenge.
2. The creator opens the Studio, chooses a character and moves, and previews the result.
3. The creator submits the creation and sees it on the challenge page.

**UC-2: Vote**

1. A fan opens the challenge page and watches creations.
2. The fan votes; the system records one vote per fan per creation and updates the leaderboard.

**UC-3: Artist uploads a song**

1. A verified artist uploads a clip and details.
2. The song enters the Fresh pool and is shown to a small sample audience.
3. If its score passes the threshold, it moves to Trending and can get a full challenge.

**UC-4: Verify an artist**

1. A user submits an artist application.
2. An admin reviews it and approves or rejects it.
3. The user receives the badge if approved.

## 8. Acceptance criteria for the demo

- A new user can sign up (mock OTP is acceptable) and reach the Trending page.
- At least 3 Cameroonian songs (licensed, royalty-free or opted-in) appear on Trending.
- At least one live challenge is shown with a working countdown.
- A creator can build and submit an animation with a character and moves, synced to the clip.
- Votes are counted once per account, and the leaderboard updates live during the demo.
- The app is deployed at a public link and works on a phone.
- The mocked features (artist dashboard, payouts, sponsored challenges) are clearly shown as mock-ups or roadmap.

## 13. Technology stack and setup (proposed)

This section replaces the "tech stack to be confirmed" note in 2.3. Items marked *(decision)* are still open.

### 13.1 Stack

| Layer | Choice | Notes |
| --- | --- | --- |
| App type | **Progressive Web App (PWA)** *(decision: PWA vs native mobile app)* | One codebase, installable on phones, no app-store review, easy to demo with a link |
| Frontend | React with **Vite** | Mobile-first single-page app; React Router for navigation; talks to Supabase and the FastAPI service; environment variables use the VITE\_ prefix |
| Styling | Tailwind CSS (+ shadcn/ui components) | Fast, consistent mobile UI |
| Database | **Supabase (PostgreSQL)** | Tables from section 5 |
| Auth | Supabase Auth | Phone OTP needs an SMS provider; use a mock OTP or email/anonymous sign-in for the demo |
| File storage | Supabase Storage | Song clips and character images |
| Live updates | Supabase Realtime | Live leaderboard and vote counts |
| Backend logic | Python (**FastAPI**) *(confirmed, see 14.1)* | Trending score job, vote validation, admin actions. Row-level security and database functions in Supabase can cover the vote rules if the Python service is skipped |
| Audio | HTML5 audio or Howler.js | Playback and beat timing |
| Animation | Canvas or CSS sprites, with moves stored as JSON on a beat grid | Lightweight; no video rendering |
| PWA support | Web manifest + service worker via vite-plugin-pwa | Installable, caches static assets |
| Hosting | Vercel (frontend), Supabase (data), Render or Railway (Python service, if used) | Free tiers are enough for the demo |
| Source control | GitHub, one repository, feature branches | Short-lived branches, merge often |

### 13.2 Architecture overview

The browser (PWA) talks to Supabase for authentication, data, files and live updates. Rules that must not be bypassed (one vote per account, challenge end time, role checks) are enforced on the server side through Supabase row-level security, database constraints or the Python service, never only in the browser. A scheduled job (or a manual script in the demo) computes the trending score and moves songs from the Fresh pool to Trending.

### 13.3 Suggested repository layout

- `/docs`: this SRS and other context files
- `/web`: React (Vite) PWA
- `/api`: Python service (only if used)
- `/supabase`: SQL for tables, policies and seed data
- `/assets`: characters, sprites, demo songs (royalty-free or opted-in only)

### 13.4 Environment variables (never commit real values)

Supabase project URL, Supabase anon key, Supabase service-role key (server only), and any SMS provider keys.

### 13.5 Instructions for the AI coding assistant

- Read this SRS before writing code and follow the requirement IDs; build all **M** items before any **S** or **C** item.
- Keep the app mobile-first, light on data, and Cameroon-focused (English and French, Pidgin captions).
- Enforce voting and role rules on the server side.
- Seed the database with at least 3 songs, 1 live challenge and several sample creations so the demo works without live data.
- Prefer simple, readable code and small commits; do not add features that are not in this document.
